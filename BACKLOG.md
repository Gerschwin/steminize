Scrolling tab in time with the recording ("tab+"): manually-typed tab (the Scratchpad's Tab pane), not auto-transcribed — see the line below about why that's not planned. Tab doesn't have lyrics' one-line-per-moment structure (a tab "line" is several stacked string-rows per bar, and useful granularity is per-column/beat, not per line), so the existing LRC lyrics-follow mechanism can't just be reused as-is. Design sketch (2026-09-29):
- Data model: anchors as `{charOffset, time}` pairs (same shape as the existing markers' `{pos, name}`, just keyed into text instead of only time) — a new `ScratchState.tabAnchors?` array alongside the existing `tab` field.
- Note-level timing without tapping every note: tab is monospace specifically because column position implies rhythm, so interpolate scroll *linearly by character offset* between two time-anchored points, not just by time. A handful of per-bar taps then gets most of the note-level feel for free, for any reasonably evenly-spaced tab; tapping more anchors (down to individual notes) trades more effort for more precision — the mechanism doesn't care about granularity, it scales either way.
- Display: a second, read-only view toggled by a "Follow along" button, same pattern as lyrics-follow — auto-scrolls to keep the current bar-block visible, highlights it, and (with note-level anchors) sweeps a thin cursor across the block in sync, like a DAW playhead over text.
- Anchor-setting UI: reuse the Tap-tempo button's interaction (tap at each bar-start during playback) plus the lyrics pane's existing nudge (−/+) controls for fixing drift after the fact.
- Scroll speed still needs to run through the same tempo-adjustment math lyrics-follow already has, so it tracks correctly when the song is slowed down.
Real feature (new data model + anchor-editing UI + a new render mode), not a small extension of lyrics-follow; needs a manual sync pass per song like LRC lyrics already do.

Tab+ roadmap beyond scrolling, discussed 2026-09-29 — a staged plan, not one feature. Each stage reuses existing app pieces more than it looks:
1. Tab+ itself (above): timed scroll, no note-content understanding yet. **Built (2026-09-29)**: Scratchpad Tab pane has "Tap ⏱" (drops an anchor at the text cursor + current playback time), "Follow along" (read-only view with a cursor highlighting the whole string block, interpolated between anchors, auto-scrolling), and "Clear timing". Anchors are raw character offsets (converted to a column coordinate across the stacked systems when used, so it does not matter which string row you tap), so editing/extending the tab after tapping shifts them — re-tap after big edits. Bar lines, row labels and the second digit of a two-digit fret take no time in the interpolation. Stage 2 groundwork built: an optional rhythm line under a block of strings (w h q e s, dot = dotted, CAPITAL = rest, a note with no letter repeats the last) gives exact note lengths; `parseTab()` returns notes with string/fret/MIDI pitch/start/length. With a rhythm line, follow-along timing is exact between taps instead of guessed from column spacing. Staff view built (Tab pane > Staff): VexFlow (lazy-loaded chunk, ~720 kB) draws the tab as standard notation, following the music. Limits: notes longer than one drawable length become a note + rests (no ties yet), no key signature (sharps only), no triplets. Next: the mic-matching trainer. Follow along has a Scroll strip mode (the tab as one long line sliding past a fixed spot). Taps can be dragged (snapping to the bar grid), locked, removed and jumped to from their overview tags. Not yet: click-a-column-to-seek, a repeated passage with two times.
2. **Playing trainer**: parse the tab's characters into structured (string, fret, time) note events — new work, since today the Tab pane is free text with no structure. Map (string, fret) → expected pitch via a tuning setting (standard EADGBE by default). Compare against the *live* mic pitch during playback (reusing the Tuner's existing real-time pitch detector) with a tolerance window on pitch and timing. Going tab→pitch this way is unambiguous, unlike pitch→tab (which is why auto-transcription is ruled out below) — the tab is already the ground truth, nothing is being guessed. Feedback should stay light-touch (a right/wrong highlight on the current note, a session accuracy %) — no scores/combos/streaks; fits how this app already treats practice (speed trainer, practice log) as feedback, not a game layer.
3. **Timing accuracy**: reuse Live Input's existing latency-measurement ("Measure" button) to calibrate the mic-to-app round trip, so timing mismatches reflect actual playing, not unmeasured input lag.
4. **Staff notation**: integrate an existing notation-rendering library (VexFlow or similar) rather than building one — the pitch+rhythm data for it falls out of stage 2's parsed note events, so this is mostly a rendering integration, not new data modeling. Doesn't contradict the "sheet music not planned" line below: that's about auto-generating notation *from audio*; this is rendering notation *from already human-verified tab data*, a different and much more tractable problem.
5. **Ear-training mode**: hide the tab/staff during playback, same comparison engine underneath — a display toggle on stage 2's trainer, not new infrastructure.
6. **Speed Trainer integration**: gate the existing gradual tempo ramp-up on accuracy ("don't speed up until you're hitting N% correct") — combines two existing systems (Speed Trainer + stage 2's trainer) into an adaptive practice loop. Likely the strongest single payoff in the whole roadmap.
Best fit for short repeating riffs/solos, not whole songs — that's where hand-typing a tab is worth the effort and a tight feedback loop actually helps.

Transcription, not planned: guitar tab (string/fret guessing is poor) and sheet music (needs a big notation library; automatic rhythms need too much fixing) — both about generating notation automatically *from audio*; see the tab+ roadmap above for a different, tractable path via manually-entered, human-verified tab instead.

GPU support on Linux (WebKitGTK): currently only mitigated (avoid loading the GPU path unless a GPU is actually usable; a warning icon next to the backend chip in main.ts if it's used anyway), not fixed. Root cause is WebKitGTK's WebGPU implementation itself (the asyncify WASM build onnxruntime-web uses for it misbehaves there — the earlier OOM crash), not something app code can truly patch. Researched 2026-09-29: WASM's JSPI (JavaScript Promise Integration) is meant to replace asyncify for this and just landed in WebKit — Safari 27 beta, 2026 — but two gaps remain before it'd help here: WebKitGTK (Linux) typically trails Safari's WebKit release by months or more, and onnxruntime-web's JSPI work so far targets Node.js/React Native, not the browser WebGPU execution provider this app actually uses (no sign of a browser/JSPI option in its docs). Not close. Real near-term fix, if this ever matters enough: bypass in-browser WebGPU entirely and run GPU inference natively in Rust (`wgpu` or ONNX Runtime's Rust bindings) via Tauri IPC — a genuine architecture change to the separation engine, not a quick task. Revisit if WebKitGTK or onnxruntime-web news changes; not worth starting speculatively.
