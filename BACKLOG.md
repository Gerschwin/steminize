Scrolling tab in time with the recording ("tab+"): manually-typed tab (the Scratchpad's Tab pane), not auto-transcribed — see the line below about why that's not planned. Tab doesn't have lyrics' one-line-per-moment structure (a tab "line" is several stacked string-rows per bar, and useful granularity is per-column/beat, not per line), so the existing LRC lyrics-follow mechanism can't just be reused as-is. Design sketch (2026-09-29):
- Data model: anchors as `{charOffset, time}` pairs (same shape as the existing markers' `{pos, name}`, just keyed into text instead of only time) — a new `ScratchState.tabAnchors?` array alongside the existing `tab` field.
- Note-level timing without tapping every note: tab is monospace specifically because column position implies rhythm, so interpolate scroll *linearly by character offset* between two time-anchored points, not just by time. A handful of per-bar taps then gets most of the note-level feel for free, for any reasonably evenly-spaced tab; tapping more anchors (down to individual notes) trades more effort for more precision — the mechanism doesn't care about granularity, it scales either way.
- Display: a second, read-only view toggled by a "Follow along" button, same pattern as lyrics-follow — auto-scrolls to keep the current bar-block visible, highlights it, and (with note-level anchors) sweeps a thin cursor across the block in sync, like a DAW playhead over text.
- Anchor-setting UI: reuse the Tap-tempo button's interaction (tap at each bar-start during playback) plus the lyrics pane's existing nudge (−/+) controls for fixing drift after the fact.
- Scroll speed still needs to run through the same tempo-adjustment math lyrics-follow already has, so it tracks correctly when the song is slowed down.
Real feature (new data model + anchor-editing UI + a new render mode), not a small extension of lyrics-follow; needs a manual sync pass per song like LRC lyrics already do.

Tab+ roadmap beyond scrolling, discussed 2026-09-29 — a staged plan, not one feature. Each stage reuses existing app pieces more than it looks:
1. Tab+ itself (above): timed scroll, no note-content understanding yet. **Built (2026-09-29), reworked into engraved notation (2026-09-30):**
   - Tapping: "Tap ⏱" drops an anchor (text-cursor character offset + current playback time); "Clear timing" wipes them. Anchors are raw character offsets, converted at use to a column coordinate across the tab's stacked systems (so it doesn't matter which string row you tap), interpolated linearly between taps. Bar lines, row labels and a fret's second digit take no time in that interpolation; a bend (`7b9r7`) counts as one note. Taps can be dragged on the overview (snapping to the bar grid), locked, removed and jumped to from their green T-tags. Editing/extending the tab after tapping shifts anchor positions — re-tap after big edits.
   - Exact timing, optionally: an optional rhythm line under a block of strings (`w h q e s`, dot = dotted, CAPITAL = rest, a blank repeats the last length) gives exact note lengths instead of guessing from column spacing — "Add rhythm line" inserts one. `parseScore()` (src/lyrics/tabSync.ts) turns the tab into `{notes, bars}`: each note's string/fret/MIDI pitch/start/length/bar.
   - **Follow along** now shows the tab *engraved*, not as scrolled plain text: `drawTabScore()` (src/ui/staff.ts) draws a real VexFlow `TabStave` with fret numbers, and a compact rhythm row under it (stems/beams/dots/rests — no 5-line staff, just enough to read the timing; a `pitched` flag can show real noteheads there instead, unused currently). Slides past a fixed point in step with the music, taps permitting; highlights the fret(s) actually sounding. Replaced the old plain-ASCII scrolling-text view entirely (no more "Scroll strip" mode/button — there's only the one engraved view now).
   - **Staff** (separate, optional toggle, off by default): a full standard-notation 5-line staff underneath the engraved tab, via `drawStaff()`. Sized from the tab's own pitch range (a generous per-semitone estimate, not a live-measured exact fit — an earlier live-measurement approach is suspected to have caused a WebKitGTK-only bug where stems/beams didn't line up with noteheads; reverted). Highlights the actual note sounding, same as the engraved tab. Limits: a note longer than one drawable length becomes note + rests, not a tie; no key signature (sharps only); no triplets.
   - When both the engraved tab and Staff are on, one continuous line marks the position down through both (matching the tab's own cursor exactly, not two independently-guessed ones).
   - Two VexFlow gotchas hit and fixed along the way, worth remembering: `TabNote.setGhost(true)` is a notational "implied note" marker (parens), not "invisible" — `GhostNote` is the class for a rest that occupies time but draws nothing. And every fret digit sits on VexFlow's own solid-white eraser rectangle behind it, so the app's usual near-white text colour made every fret invisible (white-on-white) until forced to a dark fill just for that draw pass.
   - Not yet: bar numbers or a tempo marking on the engraved tab (both in the reference screenshot that prompted the rework); click-a-column-to-seek; a repeated passage having two different times.
   - Fixed after first real-app testing (2026-09-30): the rhythm row's notes were drawn as ordinary filled noteheads, not the bare-stem "rhythm slash" look of the reference — fixed with StaveNote's own per-key setKeyStyle() (transparent fill/stroke), not a post-render DOM hide, since that needs a live *attached* document (VexFlow's Element.getSVGElement() is a plain document.getElementById()) and this draws into a detached element on purpose. And the tab stave's bottom two of six lines were genuinely clipped by the SVG's own height — the vertical "TAB" glyph needs much more room above the lines than a naive lines×spacing sum accounts for; now asked for directly via TabStave.getBottomLineY() instead of guessed (originally getBottomY(), its sibling — see 2026-09-30 below for why that turned out to be the wrong one to ask). Also: the Scratchpad's own scroll went back to a plain sticky-header-over-a-scrollable-pane (a wrapped #scratchStickyTop, the same pattern .deck-top already used) instead of flex:1/flex-shrink tricks between the engraved tab and the staff — those could still leave one or the other short with nothing to reach it.
   - Layout swapped (2026-09-30) so the rhythm row sits *under* the tab stave instead of above it, matching the reference more closely. That flushed out a second sizing bug the first fix's testing hadn't hit: the rhythm row's notes default to a downward stem (VexFlow's own call, since every placeholder notehead sits on the treble stave's middle line), so the row needs headroom *below* its own reference line — while it sat above the tab, that overshoot just fell into the tab stave's own generous top padding unnoticed; once it became the last thing on the page, there was nothing below to absorb it and the stems/rests were clipped by the SVG's own declared height. Fixed by giving the row enough height outright (doubled) and removing a small double-counted offset in the tab stave's own bottom-y (its "+10" was being added a second time when placing the rhythm row beneath it).
   - Fixed same day, second pass, after the swap turned out still not tight enough and (separately) not obviously beaming: the gap between the tab and the rhythm row was a good 60-100px wider than intended, for two compounding reasons found by reading the actual rendered SVG geometry rather than trusting VexFlow's own y-parameter guesses — `TabStave.getBottomY()` (used for `TAB_H`, the tab stave's own measured height) measures down to the bottom of the stave's whole *reserved* area, not its last string line, overshooting the real line by 50-60px; switched to `getBottomLineY()`, which is the line itself. And the rhythm row's placeholder notes, pinned to the treble stave's middle line so a downward stem had somewhere to hang, sat on a line a further ~50px below the stave's own reference y by VexFlow's own note-to-line math; re-pinned to the stave's bottom line instead (the lowest one that still needs no ledger line) with the stave itself shifted up by that same, now precisely measured, amount, and the stem direction forced down explicitly (a note this low defaults to stem-up, the wrong way for this). Beaming itself was never actually broken — generateBeams() was running and grouping correctly the whole time — it just wasn't visible against a first test tab built entirely of quarter notes, which have no beams to draw; confirmed live with an eighth-note test tab. All of the above was only checkable in a Chromium browser pane during development; user-confirmed in the real app (Linux/WebKitGTK, `tauri dev`) the same day — layout holds there too.
   - One more cosmetic fix the same day: the bar-dividing line between bars poked a few px past the bottom of the tab's own 6 string lines. Turned out to be a second, unwanted bar line — the rhythm row is its own Stave underneath the tab, and by default draws its own begin/end bar lines too, a short stub that (even with numLines:0 hiding its 5 string lines) still rendered, sitting right under the tab's own bar line and reading as one over-long line. Fixed with `setBegBarType`/`setEndBarType(Barline.type.NONE)` on the rhythm stave — the tab's own bar line (unaffected) already marks the boundary on its own.
   - Fixed 2026-10-01: a dead/muted note (`x`) rendered as a huge, badly-overlapping mark instead of a neat "X" on its line. VexFlow doesn't draw the character "x" for a muted fret — it draws a music-font glyph (the "double sharp" symbol, conventionally reused as the muted-string mark) under its own `TabNote` category, distinct from `TabNote.text` (the fret digits' own category). VexFlow's metrics table sizes `TabNote.text` at 9pt but has no entry at all for bare `TabNote`, so it silently fell through to the library's global default of 30pt — over 3x the digits' own size, against this stave's deliberately compact ~13px string spacing. Traced by reading the actual rendered SVG (a `<text>` element with the right glyph codepoint already present, at `font-size="30pt"` — not literally invisible, as first suspected, just enormous and overlapping neighbouring lines) back through VexFlow's own `tabnote.js`/`metrics.js` source in `node_modules`. Fixed by pinning `MetricsDefaults.TabNote.fontSize` to match the digits', once, the first time `drawTabScore()` runs.
   - Separate report, same day: plain fret digits themselves (not the `x` glyph above) invisible against their white eraser rectangle — but only in the app's dark theme, and only ever reported from the real app (Linux/WebKitGTK); never reproduced in Chromium testing here despite trying, including with the app's own default dark theme. The digits' dark `#111` fill (the earlier white-on-white fix) relies on ordinary SVG inheritance from an enclosing `<g>` — VexFlow's own SVG context skips writing a redundant `fill` attribute on a child whose colour already matches its group's, leaning on the child inheriting it instead. Since that mechanism couldn't be faulted by reading VexFlow's source or by testing here, hardened rather than replaced: `drawTabScore()` now also sets `fill` directly as an inline style on every fret digit's own `<text>` element after drawing, which doesn't depend on inheritance or on exactly when the context's fill state was read — belt and suspenders against a gap this app has no way to reproduce and confirm fixed outright.
2. **Playing trainer**: parse the tab's characters into structured (string, fret, time) note events — new work, since today the Tab pane is free text with no structure. Map (string, fret) → expected pitch via a tuning setting (standard EADGBE by default). Compare against the *live* mic pitch during playback (reusing the Tuner's existing real-time pitch detector) with a tolerance window on pitch and timing. Going tab→pitch this way is unambiguous, unlike pitch→tab (which is why auto-transcription is ruled out below) — the tab is already the ground truth, nothing is being guessed. Feedback should stay light-touch (a right/wrong highlight on the current note, a session accuracy %) — no scores/combos/streaks; fits how this app already treats practice (speed trainer, practice log) as feedback, not a game layer. **Built (2026-09-30):**
   - Genuinely mostly-reused pieces, as hoped: `detectPitch()`/`freqToNote()` (Tuner's own pitch detector), `player.monitoring`/`monitorTimeDomain()` (Live input's monitor stream), and the same tap-anchor timeline (`charOffsetAt`/`timeline()`) the engraved tab already scrolls by — so "the note currently highlighted" and "the note being judged" are always provably the same lookup, not two independently-guessed ones.
   - Two small new pure helpers, both unit-tested: `noteGroupAt(notes, u)` (src/lyrics/tabSync.ts) — the note(s), if any, sounding at a given timeline position, chords included; and `centsFrom(freq, midi)` (src/analysis/pitch.ts) — cents distance from a *specific* target note, unlike `freqToNote()` which rounds to whichever note is nearest (a trainer needs to know a wrong note is wrong, not silently reinterpret it as the nearest right one). Tolerance is ±40 cents, looser than the Tuner's ±5 (a fretted note's own intonation wanders more than an open string settling into tune).
   - A new **Trainer** toggle next to Follow along/Staff, same `ScratchState` boolean + button pattern; turning it on also turns Follow along on if it wasn't already (needs the note box visible to colour), one-directionally — turning Follow back off later doesn't clear the trainer flag, it just goes inert until Follow's back on. Single-note matching only: `detectPitch`'s autocorrelation can't verify a full chord, so a chord counts as hit if *any* of its notes matches — a stated limitation, not hidden.
   - Right/wrong is a CSS class (`.trainer-hit`/`.trainer-miss`, `--ok`/`--bad`) toggled on the existing note-box element(s) each ~90ms tick, same self-scheduling shape as `initTuner()`'s own loop. The accuracy tally is sticky per note-group (a brief silence right after a correct hit doesn't retroactively read as a miss) and finalized only when the timeline moves past that group; resets on trainer-on, song load, and a backward jump in the timeline (loop restart/scrub back) — a fresh tally per pass, not accumulated across loops.
   - One deliberate pull-forward from stage 3 below: `loadRecLatencyMs()` (already measured via Live input's own "Measure" button, already used for take placement) is applied as a one-line position offset before the note lookup, since monitored audio lags the track by the mic round-trip — not the calibration UI stage 3 describes, just the one existing number, defaulting to 0 for anyone who hasn't measured it.
   - Verified: `tsc`/`npm test`/production build clean; in the Chromium browser pane, confirmed the toggle/auto-enable-Follow/status-message wiring directly, and — since the pane's own mic access is sandboxed and denied — confirmed the actual pitch-comparison pipeline by monkey-patching `Player.prototype.monitoring`/`monitorTimeDomain()` to return a synthetic known-frequency tone: a correctly-matched note produced "1/1 · 100%" end to end (lookup → detectPitch → centsFrom → sticky hit → tally finalized on transition). Not yet verified with a real mic in the real app — that needs the user.
3. **Timing accuracy**: reuse Live Input's existing latency-measurement ("Measure" button) to calibrate the mic-to-app round trip, so timing mismatches reflect actual playing, not unmeasured input lag.
4. **Staff notation**: integrate an existing notation-rendering library (VexFlow or similar) rather than building one — the pitch+rhythm data for it falls out of stage 2's parsed note events, so this is mostly a rendering integration, not new data modeling. Doesn't contradict the "sheet music not planned" line below: that's about auto-generating notation *from audio*; this is rendering notation *from already human-verified tab data*, a different and much more tractable problem.
5. **Ear-training mode**: hide the tab/staff during playback, same comparison engine underneath — a display toggle on stage 2's trainer, not new infrastructure.
6. **Speed Trainer integration**: gate the existing gradual tempo ramp-up on accuracy ("don't speed up until you're hitting N% correct") — combines two existing systems (Speed Trainer + stage 2's trainer) into an adaptive practice loop. Likely the strongest single payoff in the whole roadmap.
Best fit for short repeating riffs/solos, not whole songs — that's where hand-typing a tab is worth the effort and a tight feedback loop actually helps.

Transcription, not planned: guitar tab (string/fret guessing is poor) and sheet music (needs a big notation library; automatic rhythms need too much fixing) — both about generating notation automatically *from audio*; see the tab+ roadmap above for a different, tractable path via manually-entered, human-verified tab instead.

GPU support on Linux (WebKitGTK): currently only mitigated (avoid loading the GPU path unless a GPU is actually usable; a warning icon next to the backend chip in main.ts if it's used anyway), not fixed. Root cause is WebKitGTK's WebGPU implementation itself (the asyncify WASM build onnxruntime-web uses for it misbehaves there — the earlier OOM crash), not something app code can truly patch. Researched 2026-09-29: WASM's JSPI (JavaScript Promise Integration) is meant to replace asyncify for this and just landed in WebKit — Safari 27 beta, 2026 — but two gaps remain before it'd help here: WebKitGTK (Linux) typically trails Safari's WebKit release by months or more, and onnxruntime-web's JSPI work so far targets Node.js/React Native, not the browser WebGPU execution provider this app actually uses (no sign of a browser/JSPI option in its docs). Not close. Real near-term fix, if this ever matters enough: bypass in-browser WebGPU entirely and run GPU inference natively in Rust (`wgpu` or ONNX Runtime's Rust bindings) via Tauri IPC — a genuine architecture change to the separation engine, not a quick task. Revisit if WebKitGTK or onnxruntime-web news changes; not worth starting speculatively.

Possible UI change: pin the drop zone (+ Songs/Settings tabs, already sticky) at the top of the left pane so "add a song" is always in view, letting only the Library/Setlist area scroll underneath — same idea as the deck-top/lanes split on the right. Smaller win than the right pane though: the Library card already caps itself at a 260px internal scroll, so it doesn't blow out the page the way an open song's lane count does; what mostly drives `.side` scrolling is a short window height, not song count, and pinning the full static block (drop zone, "Open multitrack/folder" buttons, format row) would eat a chunk of a short viewport permanently.
