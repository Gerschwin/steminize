Idea (2026-10-04): **native audio engine (ASIO / JACK / ALSA / WASAPI-exclusive / Core Audio)** for DAW-class latency. The webview can only reach the system's shared audio server, so Live input is stuck around 20-40 ms at best. A Rust-side engine using the `cpal` crate (its `asio` and `jack` features; ASIO needs the Steinberg SDK and a licence to redistribute) would give ~3-10 ms and the driver's real reported latency (no more Measure / Line up). The catch: the song has to play through the same native stream as the input, so the mixer, EQ, SoundTouch tempo/pitch, practice transport/click/count-in and recording all move out of the worklet into Rust, with the webview only sending commands and drawing. Staged plan: (1) throwaway proof of concept on a branch, input -> output through cpal, measure the real round trip with a loopback cable on the user's Linux + USB interface; (2) only if it clearly beats the webview, move song playback and recording native behind a "Native audio" setting, keeping the web audio path as the fallback. Desktop only; the browser version keeps the current path. Windows can get most of the benefit from WASAPI exclusive without the ASIO licence.

Scrolling tab in time with the recording ("tab+"): manually-typed tab (the Scratchpad's Tab pane), not auto-transcribed — see the line below about why that's not planned. Tab doesn't have lyrics' one-line-per-moment structure (a tab "line" is several stacked string-rows per bar, and useful granularity is per-column/beat, not per line), so the existing LRC lyrics-follow mechanism can't just be reused as-is. Design sketch (2026-09-29):
- Data model: anchors as `{charOffset, time}` pairs (same shape as the existing markers' `{pos, name}`, just keyed into text instead of only time) — a new `ScratchState.tabAnchors?` array alongside the existing `tab` field.
- Note-level timing without tapping every note: tab is monospace specifically because column position implies rhythm, so interpolate scroll *linearly by character offset* between two time-anchored points, not just by time. A handful of per-bar taps then gets most of the note-level feel for free, for any reasonably evenly-spaced tab; tapping more anchors (down to individual notes) trades more effort for more precision — the mechanism doesn't care about granularity, it scales either way.
- Display: a second, read-only view toggled by a "Follow along" button, same pattern as lyrics-follow — auto-scrolls to keep the current bar-block visible, highlights it, and (with note-level anchors) sweeps a thin cursor across the block in sync, like a DAW playhead over text.
- Anchor-setting UI: reuse the Tap-tempo button's interaction (tap at each bar-start during playback) plus the lyrics pane's existing nudge (−/+) controls for fixing drift after the fact.
- Scroll speed still needs to run through the same tempo-adjustment math lyrics-follow already has, so it tracks correctly when the song is slowed down.
Real feature (new data model + anchor-editing UI + a new render mode), not a small extension of lyrics-follow; needs a manual sync pass per song like LRC lyrics already do.

Tab+ roadmap beyond scrolling, discussed 2026-09-29 — a staged plan, not one feature. Each stage reuses existing app pieces more than it looks:
1. Tab+ itself (above): timed scroll, no note-content understanding yet. **Built (2026-09-29), reworked into engraved notation (2026-09-30):**
   - Tapping: "Tap ⏱" drops an anchor (text-cursor character offset + current playback time); "Clear timing" wipes them. Anchors are raw character offsets, converted at use to a column coordinate across the tab's stacked systems (so it doesn't matter which string row you tap), interpolated linearly between taps. Bar lines, row labels and a fret's second digit take no time in that interpolation; a bend (`7b9r7`) counts as one note. Taps can be dragged on the overview (snapping to the bar grid), locked, removed and jumped to from their green T-tags. Editing/extending the tab after tapping shifts anchor positions — re-tap after big edits.
   - Exact timing, optionally: an optional rhythm line under a block of strings (`w h q e s`, dot = dotted, CAPITAL = rest, a blank repeats the last length) gives exact note lengths instead of guessing from column spacing — "Add rhythm line" inserts one. `parseScore()` (src/lyrics/tabSync.ts) turns the tab into `{notes, bars}`: each note's string/fret/MIDI pitch/start/length/bar.
   - **Follow along** now shows the tab *engraved*, not as scrolled plain text: `drawTabScore()` (src/ui/staff.ts) draws a real VexFlow `TabStave` with fret numbers, and a compact rhythm row under it (stems/beams/dots/rests — no 5-line staff, just enough to read the timing; a `pitched` flag can show real noteheads there instead, unused currently). Slides past a fixed point in step with the music, taps permitting; highlights the fret(s) actually sounding. Replaced the old plain-ASCII scrolling-text view entirely (no more "Scroll strip" mode/button — there's only the one engraved view now).
   - **Staff** (separate, optional toggle, off by default): a full standard-notation 5-line staff underneath the engraved tab, via `drawStaff()`. Sized from the tab's own pitch range (a generous per-semitone estimate, not a live-measured exact fit — an earlier live-measurement approach is suspected to have caused a WebKitGTK-only bug where stems/beams didn't line up with noteheads; reverted). Highlights the actual note sounding, same as the engraved tab. Limits: a note longer than one drawable length becomes note + rests, not a tie; no key signature (sharps only); no triplets.
   - When both the engraved tab and Staff are on, one continuous line marks the position down through both (matching the tab's own cursor exactly, not two independently-guessed ones).
